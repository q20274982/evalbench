# /scaffold — 交付前的必經檢查

TA 要生成或交付任何要 Calvin 照著動手的東西(TODO 註解、測試骨架、練習檔、實驗腳本、分析步驟)或依 spec 實作之前,**必先載入本檔**。載入在對話裡看得見:交了東西卻沒有載入紀錄 = 違規,Calvin 一眼可指。

## 鐵律 12|自己的缺陷自己修,不轉成 Calvin 的注意事項

TA 生的東西出問題時直接改掉,不用「記得要這樣跑」「注意這裡有耦合」把成本轉嫁給他。他的時間要花在學習主題本身,不是 debug TA 的產物;**每條 caveat 都是他要額外背的規則**。

同理,**TA 自己寫的檔案裡已寫明的事,不要再拿去問他**。可檢查動作:要問「這件事怎麼做 / 誰動手」之前,先讀自己產出檔案的檔頭,並在回覆裡寫出它寫了什麼(明文 > 推論,推論永遠是猜)。

## 鐵律 13|交付一定附「乾走表」

回覆裡**先放表、再放交付物**,一列一步:

| # | 這步要他做什麼 | 需要的輸入 | 此刻從哪來 | 做完看到什麼 |

三條硬規則:

- (a)「此刻從哪來」只能填三種來源——**環境已備好的**、**檔案裡已寫在那裡的**、**前面某一步的產出**。要填「後面某步的產出」= 步驟排錯,不能交。
- (b) 每格都填得出來才交付;填不出來 = 還沒好,照鐵律 12 自己修。
- (c) 這張表檢查的是**指示可不可依循**,不是東西跑不跑得動。

理由:「交付前自己走一遍」是看不見的內心動作,加進規則的下一個 session 就再犯。表交得出來,他五秒能掃出斷點。

## 鐵律 14|當前這步全綠才推進下一步

驗收條件 = 該步指示列的**每個**要求都達成 + 該步的驗證通過。發現缺口時,回覆**只給補缺口的指示,不附帶下一步**;同一則裡既說「這條沒寫」又說「接下來做 X」= 違規。

## § 小標(鐵律 15 在交付物上的落地)

工作簿區塊、交付物的 TODO 區塊、**驗證項的文字描述**都帶定位小標,格式 `§1.3.2`(數字 = 巢狀位置,層數不限)。TA 之後引用一律用小標,Calvin 直接跳轉。

## 途中生成的猜測題(鐵律 16)

交付物註解或 chat 裡臨時生成的「先猜再驗證」提問,問的當下寫進當前工作簿「猜的答案」區並標來源;超出當前工作簿範圍的內容要先標明來源、他點頭才收(鐵律 7)。

## 慣例(EvalBench 的機制)

1. **環境常數集中一處**:模型 API key、資料集路徑、DB 連線、embedding 模型名稱這類跟學習主題無關的常數,集中在 `~/evalbench/src/config.py`,由 `pydantic-settings` 從 `.env` 讀(**不覆蓋既有環境變數**)。本體檔只 `from config import settings`,不各自 `os.getenv`。
2. **本體檔保持單純**:`src/` 底下只放本體邏輯與真正用到的輸入常數;執行入口、中間值印出、場景常數放 `experiments/wXX/` 的驅動腳本或 `tests/`。
3. **看中間值與驗證走同一個入口**:要看中間值就在 `pytest` 裡用 `-s` 印出來,同一次跑同時下斷言。**印出來的東西同時就是工作簿「實驗證據」的產出**——不要為了看中間值另外寫一支 debug 腳本,那份輸出不會進工作簿。
4. **生成即備好可跑入口**:新交付物生成時附一個能立刻跑的指令(`uv run pytest tests/test_xxx.py -s` 或 `make break`),不要讓他做到一半才發現沒環境。
5. **外部環境自備**:實驗要用的 Postgres / 資料集 / OTel demo,由交付的腳本或 `compose.yaml` 建立到需要的狀態。**測試用的 DB 與他手動開的那份不要共用**(用不同 schema 或不同 port),否則深實驗會把他的資料弄髒。
6. **斷言的比對基準必須獨立於被測的東西**:判準一句話——「這條斷言的右邊,是不是左邊算出來的?」是 = 無效,不管過不過。
   **這個專案的合法基準只有三種**:
   - `ground_truth.yaml`(IBM SRE 標的,完全外部)
   - 驗證流程自己送的場景常數(例如「我注入了 `paymentServiceFailure`,所以根因就是它」)
   - 從真實觀測抄下並註明來源的已知值
   **⚠️ 絕對不合法的基準**:模型自己的輸出、judge 自己的評分、系統自己算出來的檢索命中率。
   而且**基準要就地列在那一步旁邊**,不要只寫在檔案頂端——常數離斷言太遠 = 不在視線內,而**假的通過訊號比失敗訊號危險**。
   > 這條在 EvalBench 特別重要:整個專案就是一台量尺。**量尺自己校準自己,是這個專案最容易犯、也最致命的錯**——而且它跟 INV-13(標準答案不准洩漏)是同一件事的兩面。
7. **收尾時把引導改寫成結論**:交付物完成、要收進紀錄前,把引導註解改寫成實驗結論、拿掉 `TODO N|` 前綴、刪掉已完成的指示區塊;Calvin 寫在註解裡的答案要併進去。**改寫過的檔案是幾個月後回頭查得到的筆記。**

## 這個專案特有的一條

**任何交付物裡出現評測分數,一律帶區間**(鐵律 18)。TA 自己在乾走表的「做完看到什麼」欄寫「看到分數 62%」= 違規,要寫「看到三次跑分與它們的區間」。理由:Calvin 要學的就是這件事,TA 在交付物裡示範錯的做法,比不做還糟。
